# 0003: Guest and user accounts

- Status: accepted
- Date: 2026-11-04
- Amends: [0001](0001-stack-and-scope.md) (Users: single user, no auth)

## Context
ADR 0001 ships a single user with no auth. The MVP now has two tiers: guests with a private, expiring cookie session and no account, and registered users who sign in with email and password, Google or GitHub. Each document and chat must belong to exactly one of them, every query must stay inside that owner, and a guest's data must move to the account when the guest registers or logs in. Limits per tier are in [requirements.md](../architecture/requirements.md).

## Decision
- **Ownership: one `owners` table.** Each `users` row and each `guests` row points to its own `owners` row. `documents` and `chats` get one `owner_id NOT NULL` foreign key to `owners`. A request resolves its cookie to one `owner_id` once, and every repository query filters on it.
- **Migration on register or login:** in the login transaction, first `SELECT ... FROM owners WHERE id = :guest_owner FOR UPDATE`, then `UPDATE documents SET owner_id = :user_owner WHERE owner_id = :guest_owner`, the same for `chats`, then delete the guest and its owner row and clear the guest cookie. If the guest's owner row is already gone at the lock (the purge won), there is nothing to migrate and the login succeeds; only a failure while moving rows fails the login. The same row lock is taken by the purge and by every write that depends on a guest-owned row (the R9 document insert, chat creation and the message insert), so an in-flight upload, new chat or message cannot commit to a deleted owner; it finds the owner row (or the chat) gone and returns `401 session_expired`, and the client refreshes its session state and retries. The assistant message is inserted after the stream ends, when the response is already `200`: after a migration it succeeds under the user's owner, because the chat id does not change; if a purge deleted the chat, the insert is dropped and logged at info level, with no error to the client. Nothing else moves: objects are keyed by document UUID, vectors by `document_id`, and checkpoints by chat id. The user cap is not applied to migrated documents.
- **Tables (the migration owns the columns):** `owners`, `users`, `oauth_accounts` (one row per provider identity), `sessions`, `guests`, `chats`, plus `owner_id` on `documents` and `chats`. A chat id is its LangGraph thread id.
- **Tokens:** guest and session tokens are 32 random bytes; the database stores only their SHA-256 hash. Each has a fixed `expires_at` (`GUEST_TTL_DAYS`, `SESSION_TTL_DAYS`). Cookies (`ragidy_session`, `ragidy_guest`, `ragidy_oauth`) are `HttpOnly; SameSite=Lax`, plus `Secure` when `PUBLIC_BASE_URL` uses `https`; on `http` it is omitted, because http cookies cannot be secure and Safari may refuse `Secure` on `http://localhost`. Production must use `https`. Logout deletes the session row. Every login deletes the incoming session row, if any, and issues a new token (no session fixation).
- **Passwords:** argon2id through `argon2-cffi`, with its defaults and rehash on login.
- **OAuth flow:** authorization code with PKCE (`S256`) and `state`. `/start` stores state, verifier and provider in a 10-minute cookie (same attributes as above, `Secure` only on `https`) signed with `AUTH_SECRET` (HMAC from the standard library), then redirects. The callback checks the signature, expiry and state, exchanges the code, and reads the identity from the provider's API over TLS (Google userinfo, GitHub `/user` and `/user/emails`), so no ID-token validation is needed. Each provider is one entry in `app/core` (endpoints, scopes, identity mapping) and is enabled when its client id is set.
- **Linking rule:** a known `(provider, provider_user_id)` logs in. Otherwise, when the provider asserts a verified email that matches a user (both trimmed and lowercased; `users.email` has a unique index on that normalized form), link to that user. A verified email with no match creates a user with that email. Without a verified email, create a new user with no email. Linking to a user that has a password clears the password and deletes that user's other sessions, because email registration is unverified and could be a squatter's. Accepted risk: a squatter's documents and chats stay in the account; the user sees them in the document and chat lists and can delete them.
- **One origin:** the browser reaches the API under `<PUBLIC_BASE_URL>/api`; Vite (dev) and the web container (production) proxy `/api/*` to the API and strip the prefix. Cookies stay first-party and no CORS is needed. The OAuth redirect URI is `<PUBLIC_BASE_URL>/api/auth/oauth/{provider}/callback`.
- **CSRF and abuse:** `SameSite=Lax` plus an `Origin` check on every state-changing request: an exact string match against `PUBLIC_BASE_URL`, normalized to a lowercase scheme and host with the default port dropped. In-memory rate limits on register, login, login failures per (email, IP), guest creation per IP, and chat messages per owner; expired windows are pruned, so rotated keys cannot grow memory without limit. The IP key is the full address for IPv4 and the `/64` prefix for IPv6, because one IPv6 client controls a whole `/64`. An IPv4-mapped peer (`::ffff:a.b.c.d`) is unwrapped with `ipaddress.IPv6Address.ipv4_mapped` and keyed as its full IPv4 address. The key function never raises: a missing peer (`scope["client"]` is `None`) gets one shared key, `"unknown"`, and a host that is not a valid IP (TestClient's `"testclient"`) is keyed by its raw string. The client IP is the socket peer; forwarded headers count only from a peer in `TRUSTED_PROXIES`, through uvicorn's `ProxyHeadersMiddleware` (`trusted_hosts` gets `TRUSTED_PROXIES` normalized to strings such as `10.0.0.0/8` and `192.168.1.1/32`, the form it takes) with the server's own proxy-header handling off (`--no-proxy-headers`). No new dependency.
- **Purge:** at least once an hour the worker deletes expired sessions and, for each expired guest, takes `SELECT ... FOR UPDATE` on its `owners` row, re-checks the guest's `expires_at` under that lock (skipping a guest that was migrated or deleted), then deletes vectors, objects, checkpoints, then rows. A crash leaves the guest expired, so the next run finishes it. Lookups already ignore expired rows, so the purge timing never exposes data.

## Alternatives
- **Nullable `user_id` and `guest_id` with a check constraint:** no extra table, but every query needs a two-way filter, each table gets two foreign keys and two indexes, and a filter mistake leaks data.
- **Guests as `users` rows with a flag:** one table, but auth queries must exclude guests, `email` rules must allow nulls, and the guest purge deletes from the table that holds real accounts.
- **JWT in localStorage:** readable by any XSS, and logout cannot revoke it without a server-side list, which is a session table again.
- **Auth SaaS (Auth0, Clerk and others):** less code, but a paid external dependency, user data outside our Postgres, and guests still need our own cookie sessions.
- **Separate API origin with CORS:** no proxy, but credentialed CORS, cross-site cookies (`SameSite=None`) and a second origin to check.
- **One shared guest space:** simplest, but every guest sees every other guest's documents.
- **Picking the OAuth library here:** deferred to code. Authlib or a few `httpx` calls both fit; this ADR fixes the flow and its checks.

## Consequences
- New dependency: `argon2-cffi`. The OAuth client may add one more.
- The guest tier is public and anonymous, so the deferred SeaweedFS port hardening in ADR 0002 must land before any exposed deployment.
- shortcut: rate-limit and chat counters live in memory per API process, so they reset on restart and only work with one API process; move them to Postgres before running more than one API process. The owner row lock works across processes.
- The chat counter starts fresh after guest-to-user migration. This is accepted.
- Behind the web container, `TRUSTED_PROXIES` must list it, or every client shares one rate-limit key.
- Retrieval stays plain data: services pass the owner's document ids to `app/rag`, which needs no owner field in vector metadata.
- `docs/api/README.md` and `packages/shared-types` get the endpoints in requirements.md when they are built.
